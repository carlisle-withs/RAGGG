## 一、执行摘要

本次测试针对记忆系统的五个设计契约构造了确定性边界测试（T1-T5），并以真实生产数据做了分布统计（R1）。核心结论：

1. **【P0，已修复】摘要持久化在首次触发时必然失败**：`ConversationSummary` 实体主键缺少 `@GeneratedValue`，`MemoryService.doGenerateSummary` 首次保存摘要时 `save()` 必抛异常且被静默吞掉，导致**摘要写 MySQL、写 Redis、清空消息窗口三步全部不执行**——整个摘要子系统在生产环境从未成功工作过。真实库 `t_conversation_summary` 为 0 行（而有 88 条真实消息、且至少 1 个会话达到过阈值）是它的现实佐证。
2. **T1 竞态丢消息（契约违反，已确定性复现）**：摘要执行期间写入的消息，既不留在热窗口、也不进入任何摘要，从模型可见记忆中永久消失。
3. **T2 摘要覆盖断代（契约违反）**：第二次摘要的输入只含占位标记与新消息，不含旧摘要内容——摘要语义是"覆盖"而非"滚动合并"，长对话的早期信息逐段丢失。
4. **T3 冷热分层不对称（契约违反）**：Redis 消息丢失后，摘要可从 MySQL 回源，**消息不可**——所谓"冷热分层"只有半个分层。
5. **T4 上下文无预算上界（契约违反）**：单条 3 万字符消息原样进入上下文（实测输出 30021 字符），`window-size` 配置存在但从未被使用。
6. **T5 短会话冷启动完全失忆（契约违反）**：未达摘要阈值的会话在 Redis 失效后模型记忆归零，尽管 MySQL 中消息完好。
7. **R1 真实数据**：37 个会话中仅 1 个（2.7%）达到过摘要阈值，平均每会话 2.38 条消息——**按当前参数，摘要管线对 97% 以上的真实会话永不生效**。

## 二、测试方法

### 2.1 契约定义

每个测试先声明一条来自 README / 架构文档的设计契约，再验证实现是否满足：

| 编号 | 契约 | 断言失败即视为缺陷 |
|------|------|-------------------|
| T1 | 摘要执行期间新写入的消息，必须**留在热窗口或进入摘要**（至少其一） | 是 |
| T2 | 第二次摘要的输入必须**包含第一次摘要的内容**（滚动合并语义） | 是 |
| T3 | Redis 消息丢失后，冷层（MySQL）**应能重建最近消息窗口** | 是 |
| T4 | `buildContextPrompt` 输出长度**必须 ≤ 12000 字符（≈3000 token）** | 是 |
| T5 | 未达摘要阈值的短会话，Redis 失效后模型记忆**不应完全为空** | 是 |
| T6 | （特征记录，非缺陷判定）记录 `clearConversation` 的实际清理范围 | 否 |

### 2.2 测试基建

- `@DataJpaTest` 切片 + `@AutoConfigureTestDatabase(replace = NONE)`：仅装配 JPA 层，直连真实 MySQL（3307/rag_system），排除 Kafka/Milvus/ES 等无关组件的启动依赖；
- 真实 Redis（26379）验证实际序列化、TTL 与 List 语义；
- `ChatModelService` 用 Mockito mock，通过 `CountDownLatch` 在 mock 内部挂起，使"摘要正在调用 LLM"的时间窗**可以被精确控制**，从而让竞态条件从概率性问题变为确定性复现；
- 测试数据以 `memtest-` 前缀隔离，`@AfterEach` 清理 Redis key 与 MySQL 行，不污染开发数据；
- 测试方法级注解 `@Transactional(NOT_SUPPORTED)` 关闭 Spring 测试事务回滚，使异步摘要线程的持久化行为与生产一致，改为显式清理。

### 2.3 时序控制原理（T1 关键设计）

`doGenerateSummary` 的执行顺序是"读取 Redis List 快照 → 构造 prompt → 调用 LLM"。mock 在 `generate()` 入口处挂起：**当挂起发生时，List 快照必然已经完成读取**。此时主线程写入第 9 条消息，再释放挂起——由此保证第 9 条消息不可能出现在第一次摘要的输入中，使"消息既不在窗口也不在任何摘要"的判定成为确定性结论而非概率推断。

## 三、发现 #0（P0）：摘要持久化必然失败

### 3.1 现象

首轮测试执行时，T1/T2/T3/T6 全部卡在"等待摘要完成"的轮询上并超时。测试日志中出现：

```
ERROR ... [pool-4-thread-1] com.rag.application.chat.MemoryService : Failed to generate summary for conversation: memtest-...
org.springframework.orm.jpa.JpaSystemException: Identifier of entity
  'com.rag.domain.model.ConversationSummary' must be manually assigned before calling 'persist()'
```

### 3.2 根因

`ConversationSummary.java:13`：

```java
@Id
private Long id;          // 缺少 @GeneratedValue
```

而 `MemoryService.doGenerateSummary`（修复前）：

```java
ConversationSummary entity = summaryRepository
        .findByUserIdAndConversationId(userId, conversationId)
        .orElse(new ConversationSummary(conversationId, userId, null, summary));  // id = null
entity.setContent(summary);
summaryRepository.save(entity);   // ← 首次保存：persist() 要求手动赋值主键 → 必抛异常
```

异常被 `catch (Exception e) { log.error(...) }` 吞掉。**关键在于异常抛出点之后的代码全部不执行**：

```java
redisTemplate.opsForValue().set(summaryKey, summary, ...);  // 不执行
redisTemplate.delete(messageKey);                            // 不执行
redisTemplate.opsForList().rightPush(messageKey, marker);    // 不执行
```

即：摘要生成（已花费一次 LLM 调用）后，持久化、缓存写入、窗口清理三步全部静默失败，消息窗口无限累积，摘要永远不会生效。

另有一个次生缺陷被同轮测试暴露：`MemoryService` 构造实体时 `lastMessageId` 传 `null`，而该列 `NOT NULL`——即使修复主键，此处仍会触发约束异常。

### 3.3 现实佐证

对真实库（rag_system）执行 `SELECT COUNT(*) FROM t_conversation_summary` 结果为 **0**；而 `t_message` 有 88 条真实消息、且 R1 统计显示有 1 个会话的消息数达到了阈值 8。**该会话触发了摘要、调用了 LLM、然后什么都没留下。**代码缺陷与生产数据完全互证。

### 3.4 修复（最小修复，已在本次测试中应用）

1. `ConversationSummary.java`：`@Id` 补充 `@GeneratedValue(strategy = GenerationType.IDENTITY)`（表列本身已是 `AUTO_INCREMENT`，无需改表）；
2. `MemoryService.java`：构造实体时 `lastMessageId` 以空串 `""` 满足 NOT NULL 约束（该字段语义上是"摘要水位线"，当前实现从未使用——见第六节改进建议）。

修复后测试套件即出现第三节 T1-T5 的确定性结果。**注意：下述 T1-T5 的结论均基于修复 #0 之后的代码**，否则摘要成功路径根本不可达。

## 四、T1-T5 详细结果

### T1 竞态丢消息 —— 失败（缺陷确认）

**复现**：写满 8 条消息触发异步摘要 → 摘要线程进入 LLM 调用（挂起）→ 主线程写入第 9 条（含关键词"独角兽"）→ 释放挂起 → 等待两次摘要（第 9 条写入使计数达 9 ≥ 8，也会触发一次）完成。

**实测证据**：

```
[T1] 摘要 prompt 数=2 | 第9条在热窗口=false | 第9条进入过任何摘要=false
[T1] prompt[0]=请简要总结...user: 第1条消息...user: 第8条消息          ← 第一次摘要输入：仅前 8 条
[T1] prompt[1]=请简要总结...system: [早期对话已摘要]                    ← 第二次摘要输入：仅占位标记
[T1] 摘要后热窗口内容=[{"role":"system","content":"[早期对话已摘要]"}]
```

**判定与解读**：第 9 条消息在 MySQL 中完好（断言通过：9 行），但在模型可见的记忆里**双重消失**——不在热窗口（被 `delete(messageKey)` 连带清除），不在任何摘要输入中（第一次摘要快照早于它，第二次摘要只读到占位标记）。契约"至少留在窗口或进入摘要之一"被违反。

**根因**：`doGenerateSummary` 用 `redisTemplate.delete(messageKey)` 清空整个 key 而非精确截断已摘要区间。摘要执行窗口内（LLM 调用可达数秒）的所有新写入都会被这个 delete 无差别清除，且不被任何摘要捕获。

### T2 摘要覆盖断代 —— 失败（缺陷确认）

**复现**：周期一写 8 条（第 1 条含关键事实"我的知识库代号是阿尔法计划"）触发第一次摘要；周期二再写 7 条触发第二次摘要；断言第二次摘要的输入包含旧摘要内容（从而能保留阿尔法计划）。

**实测证据**（第二次摘要的完整输入 prompt）：

```
请简要总结以下对话的主要内容，保留关键信息（用户问题和助手指南）：

system: [早期对话已摘要]
user: 周期二第1条，全新话题1
user: 周期二第2条，全新话题2
...
user: 周期二第7条，全新话题7
```

**判定与解读**：输入中只有占位标记与新消息，**旧摘要内容缺席**，"阿尔法计划"无从进入第二次摘要。实现是 `entity.setContent(summary)` 直接覆盖（`MemoryService.java:253`），语义为"每 8 条断代一次的覆盖式摘要"，而非滚动合并。推论：**长对话中被摘要覆盖的早期信息永久丢失**，其记忆上限低于"不做摘要、全量保留"的朴素基线。

### T3 冷热分层不对称 —— 失败（缺陷确认）

**复现**：8 条消息触发摘要后，仅删除 Redis 消息 List（模拟 TTL 过期/实例重启），保留摘要 key，调用 `getContext`。

**实测证据**：

```
[T3] Redis 丢失后：summary 存在=true | recentMessages=0 | MySQL 行数=8
```

**判定与解读**：摘要可以从 MySQL 回源（`loadSummaryWithFallback` 有 read-through，此半边成立），消息不能（`loadMessagesWithFallback` 只读 Redis，`MemoryService.java:130-148` 无回源逻辑）。契约要求冷层能重建热层职能，实际只有半个分层：**MySQL 中的消息副本对模型完全不可见**，仅服务于前端历史回看 API。

### T4 上下文无预算上界 —— 失败（缺陷确认）

**实测证据**：

```
[T4] 单条 30000 字符消息 → buildContextPrompt 输出 30021 字符
[T4] 6×5000 字符消息   → buildContextPrompt 输出 30086 字符
```

**判定与解读**：`buildContextPrompt` 对消息内容不做任何截断或预算核算（断言上限 12000 字符 ≈ 3000 token）。真实数据中单条消息最长 5419 字符（R1），意味着**一条粘贴的长文档就能把记忆上下文推到 5k+ token 且无任何防线**。配置项 `memory.window-size` 在 `MemoryService` 中声明后从未被引用（`windowSize` 仅出现在字段声明处），是死配置。

### T5 短会话冷启动完全失忆 —— 失败（缺陷确认）

**复现**：写 3 条消息（低于阈值 8，不触发摘要）→ 删除 Redis 消息 key（模拟 TTL 过期）→ 调用 `getContext`。

**实测证据**：

```
[T5] Redis 失效后：summary=null | recentMessages=0 | MySQL 行数=3
```

**判定与解读**：与 T3 互补——T3 是"有摘要、丢窗口"的部分恢复，T5 是**全灭**：短会话（真实分布中的 98.6%，见 R1）在 Redis 失效后摘要与消息双无，模型记忆归零，而 MySQL 中 3 条消息完好。结合 Redis 7 天 TTL，这构成一个真实的用户体验悬崖：**隔一周以上回到一个未结束的会话，对话上下文完全消失**。

### T6 clearConversation 语义 —— 通过（特征记录）

```
[T6] clearConversation 后：Redis 消息=0 | Redis 摘要=false | MySQL 消息行数=2
```

**记录**：`clearConversation` 清除 Redis 双 key 与 MySQL 摘要行，但 **MySQL 消息行保留**（`t_message` 有软删除字段但未使用）。即"删除会话"≠"删除数据"，此为现状记录，供数据合规评审参考。

## 五、R1 真实数据统计

数据源：rag_system.t_message / t_conversation_summary（生产开发库真实数据）。

| 指标 | 数值 |
|------|------|
| 总消息数 / 会话数 / 用户数 | 88 / 37 / 1 |
| 会话消息数分布 | 2 条：34 个；6 条：2 个；8 条：1 个 |
| 平均 / 最大消息数 | 2.38 / 8 |
| 单条消息长度（字符） | 平均 501.5 / 最大 5419 |
| 达到摘要阈值（8 条）的会话 | 1 / 37（**2.7%**） |
| 已持久化的摘要总数 | **0** |

**解读**：

1. **摘要管线与真实负载严重错配**：阈值 8 条意味着"第 4 轮对话"才触发摘要，而 98.6% 的真实会话只有 1 轮（2 条消息）。按当前参数，摘要子系统对几乎全部真实流量是死代码，却在每个达到阈值的会话上消耗一次 LLM 调用（且修复 #0 之前连这次调用都是纯浪费——生成后必然丢弃）。
2. **真实负载下"全量保留"成本极低**：最大会话 8 条 × 平均 501 字符 ≈ 4KB 上下文。在当前规模下，不做任何摘要的记忆策略成本可忽略；摘要机制的真实价值区间（超长对话、高并发）需要 R2/第三层基准（见第七节）验证后才能确认。
3. **单条消息可达 5419 字符**：即使会话很短，单条长消息也可能主导上下文预算——这支持"按 token 预算而非条数控制上下文"的改进方向（对应 T4）。

## 六、结论与改进方向索引

测试确认的缺陷按严重级排序：

| 级别 | 发现 | 对应改进方向 |
|------|------|-------------|

## 七、本次测试的边界（威胁有效性因素）

1. **LLM 为 mock**：T1/T2 验证的是摘要机制的输入/输出契约（prompt 内容、窗口状态），不评估真实 LLM 摘要的语义质量——后者属于第三层端到端基准（多轮记忆问答 + LLM-as-judge）的范围。
2. **单实例时序**：T1 的竞态在单线程摘要执行器下确定性复现；生产若提高 `memorySummaryThreadPoolExecutor` 并发度，竞态窗口会有变化，但 `delete` 全清的根因不变，结论外推有效。
3. **R1 样本量**：88 条消息为开发期真实数据，分布（会话普遍很短）可能与实验室上线后的负载不同——这也是"先接入评测、再调参数"的原因而非结论缺陷。
4. **测试期间的代码变更**：发现 #0 的两处最小修复已应用于工作区（`ConversationSummary.java`、`MemoryService.java`），T1-T5 结果基于修复后代码。修复 diff 未提交，建议随本报告一并评审提交。

### 8.3 实施过程中的两个次生发现

1. **`@DataJpaTest` 测试管理事务的坑**：类上标注 jakarta 的 `@Transactional(TxType.NOT_SUPPORTED)` 不会挂起 Spring 测试事务——主线程写入停留在未提交事务中，jdbcTemplate（同事务连接）可见而异步线程连接（REPEATABLE READ 快照）不可见，造成"重建返回空"的假象。必须使用 Spring 的 `@Transactional(propagation = Propagation.NOT_SUPPORTED)`。该坑对今后所有涉及异步线程 + DB 断言的切片测试适用。
2. **v3 SSE 控制器完全没有接入记忆**：`RagChatController`（`/api/v1/rag/v3/chat`）注入了 `MemoryService` 但从未调用（不读记忆、不存消息，请求参数中也无 userId）。修复需要 API 契约变更（增加 userId 参数 + 前端配合），列为遗留项，未在本轮实施。

### 8.4 遗留项

- **v3 SSE 路径的记忆接入**（见 8.3-2）；
- **C1-C6 端到端记忆基准**（多轮指代/约束保持/跨摘要边界等真实 LLM 问答评测，量化 L5 修复的检索命中率收益）需要真实 LLM API 配额，尚未执行；
- `clearConversation` 的 MySQL 消息保留语义待产品/合规确认；
- 建议为 Grafana 增加 memory.* 指标面板与 `memory.summary.total{result=fail}` 告警规则。

## 九、500 次迭代随机化 Soak 测试（2026-09-05，修复实施后追加）

### 9.1 动机与结构

确定性边界测试（T1-T7）只能证明"单点正确"，无法证明"统计可靠"——尤其是竞态修复必须在不同随机交错下反复锤打。Soak 测试（`MemoryServiceSoakTest`）共 **500 次迭代**：

| 场景 | 迭代数 | 内容 |
|------|--------|------|
| A 随机场景 | 200 | 随机消息数（3-20）/长度分布（80% 短、15% 中、5% 长）、随机触发条数/token 摘要、随机模拟 Redis 失效（195 次真实发生）与恢复读取 |
| B 并发写入 | 150 | 2-4 写线程并发 addMessage（共 1990 条），LLM 延迟逐轮随机化（0-25ms），锤打竞态窗口（161 次摘要） |
| C 多会话交错 | 150 | 4 会话轮转写入（1948 条）共享 4 线程摘要池，校验隔离性与并发上限 |

每次迭代校验 6 项不变量：I1 无丢失（每条消息 ∈ 窗口 ∪ 摘要，token 回声桩使摘要链全量可追踪）、I2 无复活（窗口消息 id > 水位线）、I3 有界性、I4 持久性、I5 单会话摘要并发 ≤1、I6 会话隔离。固定随机种子（20260905，`-Dsoak.seed` 可覆盖）保证可复现，失败信息携带迭代号/种子/会话 id。本轮总不变量校验 **12234 次**，其中 34 次"暂态"（摘要在途 + 失效恢复守卫的合法中间态）全部在静默对账后自愈。

### 9.2 Soak 发现的三个真实缺陷（全部为确定性测试盲区）

Soak 上线后前几轮运行即以不同迭代号（12、45、24、50、87、108）暴露了三个边界测试无法覆盖的缺陷，逐一定位根因并修复：

**缺陷 S1：LTRIM 快照索引错位（消息丢失）**
- 时间线：摘要快照读取后，并发的窗口缺口补齐（leftPush 前插）改变列表内容 → 摘要按过期索引 `LTRIM` 切掉既不在窗口、也不在任何摘要里的消息。
- 修复：`LTRIM` 按索引截断 → **`LREM` 按值精确删除**（只删本次摘要覆盖的快照条目，对并发补齐/新写入免疫）。

**缺陷 S2：id 分配序 ≠ 推入序（水位线语义破坏）**
- 时间线：写线程 A 拿到自增 id=5816 后暂停，写线程 B 拿到 5817 先推入；摘要快照含 5817 → 水位线越过尚未推入的 5816 → 该消息既不会被摘要覆盖、也不会被缺口补齐（id < 水位线）。
- 修复：**会话级写锁**——同一会话的"MySQL 落库（分配 id）→ Redis 推入"成对原子，保证 id 序 == 推入序，水位线语义严格成立。

**缺陷 S3：幽灵窗口对账（整批消息丢失）**
- 时间线（迭代 12 完整复盘）：S2 摘要读取窗口（7 条）→ 主线程 add 第 8 条并模拟 flush（清空窗口）→ S2 的对账使用**过期的调用方窗口**计算 presentIds → 误判"只缺 1 条"（实际全缺 7 条）→ 快照=[第 8 条] → 水位线=最后一条 id → 前 7 条成为永久孤儿。
- 修复：**`reconcileWindow` 拿锁后强制重新读取窗口**，绝不信任调用方传入的快照；同时**摘要前必须先对账**（reconcile-before-snapshot），保证任何摘要的快照都是连续无洞的窗口，水位线不会跳过未摘要消息。

### 9.3 修复后验证结果

```
边界回归 T1-T7：7/7 通过
Soak-A 200 次随机场景：全部通过（写入 2209，摘要 206，窗口补齐 195，模拟失效 195，暂态自愈 34）
Soak-B 150 次并发写入：全部通过（写入 1990，摘要 161）
Soak-C 150 次多会话交错：全部通过（写入 1948）
全项目：19/19 通过（ChunkStrategy 9 + 边界 7 + Soak 3）
```

### 9.4 Soak 阶段的次生发现

- `t_message.content` 为 TEXT 列（64KB），单条超过 ~2.1 万 CJK 字符的消息会导致 MySQL 持久化失败（`Data too long`），该消息降级为仅存在于 Redis 窗口（id=null）。长文档粘贴场景建议改 MEDIUMTEXT 或入库前截断。
- Soak-C 的会话消息数（2-5 条/会话）未达到摘要触发条件，其 150 次迭代实际未覆盖摘要路径——并发摘要路径由 Soak-B 覆盖。后续可给 Soak-C 增加长消息以补足。

### 9.5 方法论结论

这一轮 soak 的价值曲线非常清晰：**7 个确定性测试证明"设计意图被实现"，500 次随机迭代证明"实现在任何交错下都不坏"**。三个缺陷（S1-S3）全部位于确定性测试无法枚举的交错空间里，且每一个的修复都以完整时间线复盘为依据——这正是"至少 500 次测试"要求的意义所在。测试代码与全部修复已就位，可作为长期回归资产：`mvn test -Dtest='MemoryServiceBoundaryTest,MemoryServiceSoakTest'`。
