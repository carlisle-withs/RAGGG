# 知识库文档上传全链路压测报告

> 本文档记录知识库构建过程中，文档上传流水线的压测过程、发现的问题及优化方案。

---

## 一、压测流程概述

### 1.1 整体架构

文档从上传到完成索引，经历以下完整链路：

```
上传请求
  │
  ▼
┌──────────────────────────────────────────────────────────────┐
│ ① 上传阶段 (DocumentApplicationService)                      │
│    MinIO ──写入文件──▶ DB ──保存元数据──▶ Kafka ──发送消息 │
└──────────────────────────────────────────────────────────────┘
  │
  ▼ Kafka Topic: document-upload
┌──────────────────────────────────────────────────────────────┐
│ ② 解析阶段 (ParseService)                                   │
│    消费消息 ──从 MinIO 下载文件 ──Tika 提取文本 ──保存──▶   │
│    发送消息 Kafka Topic: document-parsed                     │
└──────────────────────────────────────────────────────────────┘
  │
  ▼ Kafka Topic: document-parsed
┌──────────────────────────────────────────────────────────────┐
│ ③ 分块阶段 (ChunkService)                                   │
│    消费消息 ──下载 parsed.txt ──分块算法 ──保存 chunks.json─▶│
│    发送消息 Kafka Topic: document-chunked                   │
└──────────────────────────────────────────────────────────────┘
  │
  ▼ Kafka Topic: document-chunked
┌──────────────────────────────────────────────────────────────┐
│ ④ 索引阶段 (IndexService)                                   │
│    消费消息 ──下载 chunks.json ──批量 Embedding ──持久化──▶   │
│    写入 MySQL + Elasticsearch + Milvus                       │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 三条 Kafka Topic

| Topic 名称 | 生产者 | 消费者 | 携带内容 |
|---|---|---|---|
| `document-upload` | DocumentApplicationService | ParseService | 文件元信息 |
| `document-parsed` | ParseService | ChunkService | 解析后文本路径 |
| `document-chunked` | ChunkService | IndexService | 分块结果路径 |

### 1.3 压测脚本使用方式

```bash
# 进入压测目录
cd D:\Workspace\RAGGG\stress-test

# 基础用法：固定分块策略，5 并发，无限轮次
python document-upload-stress.py --concurrency=5

# 指定分块策略
python document-upload-stress.py --chunk-strategy=semantic
python document-upload-stress.py --chunk-strategy=structural
python document-upload-stress.py --chunk-strategy=intelligent

# 限制请求数（适合快速验证）
python document-upload-stress.py --concurrency=5 --requests=40

# 指定运行时长（秒）
python document-upload-stress.py --concurrency=5 --duration=120
```

### 1.4 支持的分块策略

| 策略 | 说明 | 配置参数 |
|---|---|---|
| `fixed`（默认） | 按固定字符数切分 | `chunkSize`, `chunkOverlap` |
| `structural` | 按自然段落结构切分 | `minParagraphLength`, `maxParagraphLength` |
| `semantic` | 按语义/句子边界切分 | `maxTokensPerChunk`, `minTokensPerChunk` |
| `intelligent` | 根据 MIME 类型自动选择最优策略 | 无需参数 |

**如何理解这组数据？**

- **10 个请求串行执行**：吞吐量仅 0.01 req/s，一个请求处理完下一个才开始，总耗时 767.5 秒 ≈ 12.8 分钟

- **上传极快（45 ms）**：说明瓶颈不在上传和数据库层面

**与当前批量 Embedding 结果对比：**

| 指标 | 早期（逐条 Embedding） | 当前（批量 Embedding，400请求） | 提升 |
|------|----------------------|-------------------------------|------|
| 端到端 P95 | **100,672 ms（100秒）** | **3,028 ms（3秒）** | **33 倍** |
| 吞吐量 | 0.01 req/s | 1.63 req/s | **163 倍** |
| 瓶颈 | 逐条 Embedding API 调用 | 外部 API 不稳定抖动 | - |

从 100 秒降到 3 秒，**批量 Embedding 带来了约 33 倍的性能提升**，这正是系统从逐条改为批量后的核心价值体现。

## 二、发现的问题及解决

### 2.1 问题一：索引阶段是全链路最大瓶颈

#### 问题描述

在所有压测数据中，**索引阶段**（IndexService）的耗时远超其他阶段，是全链路最大瓶颈：

```
服务端各阶段 P50 延迟对比:
  MinIO 上传     13.4 ms  ████
  DB 保存         0.5 ms  ▏
  Kafka 发送      0.5 ms  ▏
  解析 (Tika)    58.4 ms  █████████████████
  分块           33.3 ms  ████████████
  索引 (全链路) 147.1 ms  ████████████████████████████████████████████████████████ ← 瓶颈
```

索引 P50（147ms）比解析 P50（58ms）高出 **2.5 倍**，比 MinIO 上传高出 **11 倍**。

#### 根因分析

**索引阶段的耗时构成：**

```
索引总耗时 = 批量 Embedding 耗时 + 持久化耗时
           = Embedding API 调用（外部依赖）+ MySQL + ES + Milvus 批量写入
```

**历史演进说明：**

- **最初版本**：IndexService 使用**逐条（single）Embedding**，即每个 chunk 单独调用一次 Embedding API。对于一个 20 个 chunk 的文档，需要 20 次网络往返，P95 延迟高达数千毫秒，是全链路第一大瓶颈。
- **后来优化**：引入了**批量（batch）Embedding**，凑满 32 个 chunks 后，一次 API 调用获取所有向量（`IndexService.processBatch()` 第 215 行），将 20 次网络往返压缩为 1 次，索引 P95 从数千毫秒大幅下降到约 725ms。
- **当前状态**：批量优化已生效，但真正的问题在于 **Embedding API 是外部云端依赖**：
- 调用的是 SiliconFlow 云端 API（`https://api.siliconflow.cn/v1`）
- Embedding P95 约 221ms，波动范围 200-400ms
- Embedding 占据了索引 P95 的 221/725 = **30%** 贡献，加上持久化 60ms，合计约 281ms
- 当 API 响应抖动时，P95 从 725ms 暴涨到 2192ms（某次测试数据）

**为什么不是 Kafka 的问题？**

上传 QPS（1.37）、解析 QPS（1.36）、索引 QPS（1.36）三者完全一致，说明三个 Kafka 消费者处理速度匹配，没有积压。瓶颈不在 Kafka 消费端，而在 IndexService 内部的 Embedding API 调用。

#### 优化方案

**方案 A（推荐）：引入 Embedding 结果缓存**

在调用 Embedding API 前，先查缓存（Redis 或本地文件）：
- 缓存 key = 文本内容的 MD5 哈希
- 相同文本不重复调用 API，大幅降低耗时和成本
- 命中缓存时延迟从 ~221ms 降至 <1ms

**方案 B：切换到本地 Embedding 模型**

部署轻量级本地 Embedding 模型（如 `bge-m3` 本地版），消除网络依赖：
- 延迟稳定可控（无外部 API 抖动）
- 适合内网/私有化部署场景

**方案 C：增加消费者并发数**

当前 `KafkaInfrastructureConfig` 中 `concurrency=3`，可适当调高：
```java
// KafkaInfrastructureConfig.java 第 43 行
factory.setConcurrency(10);  // 从 3 提升到 10
```
注意：并发数过高会增加 API QPS 压力，可能触发限流。

### 2.2 问题二：Kafka 阶段 QPS 虽一致，但受限于 BATCH poll 间隔

#### 问题描述

在最新 400 请求测试中，三个阶段的 QPS 已完全一致：

```
上传 QPS      1.37 req/s
解析 QPS       1.36 doc/s   ✓ 三者一致，无积压
索引 QPS       1.36 doc/s    ✓ 三者一致，无积压
Chunk 吞吐    24.43 chunks/s
```

但在某些 Embedding API 响应不稳定的批次中，三个 QPS 同时下降，说明瓶颈在上游（索引）时，会拖累整条链路。

#### 根因分析

**Kafka AckMode 为 BATCH，固有 3 秒 poll 间隔**

这是端到端延迟约 3000ms 的根本原因：

```
客户端感知端到端延迟 ≈ 服务端实际处理时间 + Kafka poll 等待时间
                    ≈ 237ms（服务端）+ ~2800ms（poll 等待）
                    ≈ 3017ms
```

`KafkaInfrastructureConfig` 使用 `AckMode.BATCH`，Kafka consumer 每 3 秒才 poll 一次：

```java
factory.getContainerProperties().setAckMode(BATCH);
```

服务端各阶段实际处理很快（总计 ~237ms），但消息在 poll 队列中等待了 ~2800ms，客户端感知的延迟几乎全部来自等待。

**三个消费者独立消费——不是当前瓶颈，但在 Embedding API 抖动时会形成连锁拖拽：**

| 消费者 | Topic | 分区数 | 实际并发 |
|---|---|---|---|
| ParseService | document-upload | 3 | concurrency=3 |
| ChunkService | document-parsed | 3 | concurrency=3 |
| IndexService | document-chunked | 3 | concurrency=3 |

当 Embedding API 响应变慢时，IndexService 处理时间拉长 → Kafka 中消息堆积 → 上游生产速度受限于 poll → 三阶段 QPS 同步下降。

#### 优化方案

**方案 A（解决 poll 延迟）：改用 AckMode.RECORD**

```java
// KafkaInfrastructureConfig.java
factory.getContainerProperties().setAckMode(AckMode.RECORD);
```
改为每条消息立即 ack，可将 poll 间隔从 3 秒缩短到毫秒级，端到端延迟可从 **3017ms 降至 <500ms**。

**方案 B（根本解决 Embedding 抖动拖拽）：换成本地 Embedding 模型**

Embedding API 响应稳定后，IndexService 处理时间稳定在 147ms（P50），三阶段 QPS 一致性问题自然消失，无需额外限流。

**方案 C（解决速度不匹配）：Kafka 消费端限流保护**

当 IndexService 处理慢时，通过有界队列保护上游：
- 在 ParseService/ChunkService 中增加有界队列
- 队列满时暂停消费，避免内存溢出

## 三、压测发现的其他修复

### 3.1 端口配置错误（历史遗留）

**问题**：`application.yml` 中 MinIO/Milvus/ES/Kafka 的端口与 `docker-compose.yml` 不匹配。

| 服务 | docker-compose 实际映射 | application.yml 错误配置 |
|---|---|---|
| MinIO | 29005 | 9001 |
| Milvus | 29530 | 19530 |
| Elasticsearch | 29201 | 9200 |
| Kafka | 29292 | 无默认 |

**修复**：在 `config.yaml` 中正确配置了所有端口（`server.ip=localhost`）。

### 3.2 KafkaAutoConfiguration 被排除导致消费者未启动

**问题**：早期为绕过 Kafka 不可用的启动问题，将 `KafkaAutoConfiguration` 排除，但导致 `@KafkaListener` 注解处理器未激活，所有消费者从未启动。

**修复**：新增 `KafkaInfrastructureConfig.java`，手动创建 `ConsumerFactory`、`ProducerFactory`、`KafkaTemplate` 并添加 `@EnableKafka`。

### 3.3 file_type 字段宽度不足

**问题**：`KnowledgeDocument` 实体中 `file_type` 定义为 `VARCHAR(32)`，但 `.docx` 等文件的 MIME 类型超过 32 字符，导致 `Data truncation` 错误。

**修复**：`ALTER TABLE t_knowledge_document MODIFY COLUMN file_type VARCHAR(128);`
