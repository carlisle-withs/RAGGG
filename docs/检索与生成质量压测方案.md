## 二、测试指标体系

### 2.1 检索质量指标（Retrieval Quality）

需要**人工标注标准答案**才能计算。

```
标准答案文件格式 (ground_truth.json):
{
  "query_id": "q1",
  "query": "Kafka 消费组 lag 如何监控",
  "relevant_chunk_ids": ["chunk_001", "chunk_003", "chunk_017"],
  "note": "包含 JMX 监控和 Kafka Manager 两种方案"
}
```

| 指标 | 计算方式 | 目标值 |
|------|---------|--------|
| **Recall@K** | 检索到的相关 chunk 数 / 标准答案总数 | ≥ 0.80 @top5 |
| **MRR** | Mean Reciprocal Rank，所有查询的正确 chunk 首次出现位置的倒数均值 | ≥ 0.60 |
| **NDCG@K** | 归一化折损累计增益，考虑排序位置的重要性 | ≥ 0.70 @top5 |
| **MRR@K** | 仅看 topK 内的首次命中 | ≥ 0.75 @top5 |
| **检索空结果率** | 返回 0 条结果的查询占比 | < 5% |
| **TopK 覆盖率** | 每种查询类型（短/中/长）Top5 至少命中 1 个相关 chunk 的比例 | ≥ 85% |

### 2.2 生成质量指标（Generation Quality）

生成质量的评估最复杂，业界有三条路线：

| 评估路线 | 方法 | 优点 | 缺点 |
|---------|------|------|------|
| **人工评估** | 专家打分 1-5 分 | 最准确 | 成本高、无法自动化 |
| **LLM as Judge** | 用 GPT-4/Claude 等强模型评分 | 可自动化、成本低 | 有偏差、需 prompt 设计 |
| **基于标准答案** | ROUGE/BLEU 等文本相似度 | 完全自动化 | 不适合开放式回答 |

**推荐方案：LLM as Judge + 人工抽检**

```
评判 Prompt（英文以减少模型偏见）:

You are an expert evaluator. Score the following AI answer on 4 dimensions.
Each score must be 1-5 (1=poor, 5=excellent).

Question: {question}
Reference (relevant knowledge): {reference_chunks}
Answer: {generated_answer}

Evaluate:
1. **Relevance**: Does the answer address the question?
2. **Accuracy**: Is the answer factually correct based on reference?
3. **Completeness**: Are all aspects of the question covered?
4. **Coherence**: Is the answer well-structured and clear?

Output JSON:
{
  "relevance": 1-5,
  "accuracy": 1-5,
  "completeness": 1-5,
  "coherence": 1-5,
  "hallucination": "none/minor/moderate/severe",
  "overall": 1-5,
  "reasoning": "brief explanation"
}
```

### 2.3 性能指标（Performance）

| 指标 | 定义 | 目标值 |
|------|------|--------|
| **检索 P95 延迟** | 从请求到 RRF 融合完成 | < 500ms |
| **Embedding 查询延迟** | 单次 query embedding | < 200ms |
| **Milvus 向量检索延迟** | TopK×2 的 ANN 搜索 | < 50ms |
| **ES BM25 检索延迟** | 全文检索 | < 100ms |
| **RRF 融合耗时** | 两路结果合并排序 | < 5ms |
| **生成首 Token 延迟 (TTFT)** | 用户发起请求到收到第一个字的时间 | < 1.5s |
| **生成总延迟** | 完整回答生成时间 | < 10s（取决于回答长度）|
| **端到端 RAG 延迟** | 检索 + 生成整体 | < 15s |
| **并发 QPS** | 检索服务最大吞吐量 | ≥ 50 req/s |
| **错误率** | HTTP 5xx 或超时占比 | < 1% |

### 2.4 用户体验指标（UX）

| 指标 | 定义 | 目标值 |
|------|------|--------|
| **流式输出率** | SSE 每秒输出 token 数 | ≥ 20 tokens/s |
| **中途断开率** | 用户在生成中途断开连接的比例 | < 10% |
| **"未找到"正确率** | 知识库无相关内容时，模型正确回答"未找到"的比率 | ≥ 90% |
| **多轮上下文保持率** | 第二轮对话能正确引用第一轮内容的比率 | ≥ 80% |

### 3.2 新增脚本一：test-retrieval-quality.py

**目标**：评估检索质量（Recall、MRR、NDCG），需要预先上传测试文档并标注标准答案。

```python
"""
检索质量评估脚本

测试流程：
1. 加载 ground_truth.json（人工标注的相关 chunk ID）
2. 对每条 query 调用 /api/v1/retrieve 接口
3. 计算 Recall@K、MRR@K、NDCG@K
4. 输出质量报告

使用方法：
python test-retrieval-quality.py
python test-retrieval-quality.py --kb=1 --topk=5
python test-retrieval-quality.py --export-csv=results.csv
"""

# ========== 核心指标计算 ==========

def recall_at_k(retrieved_ids: List[str], relevant_ids: set, k: int) -> float:
    """Recall@K = 命中的相关文档数 / 标准答案总数"""
    retrieved = set(retrieved_ids[:k])
    return len(retrieved & relevant_ids) / len(relevant_ids) if relevant_ids else 0

def mrr_at_k(retrieved_ids: List[str], relevant_ids: set, k: int) -> float:
    """MRR@K = 所有查询中，第一个相关文档出现位置倒数的均值"""
    for i, doc_id in enumerate(retrieved_ids[:k]):
        if doc_id in relevant_ids:
            return 1.0 / (i + 1)
    return 0.0

def ndcg_at_k(retrieved_ids: List[str], relevant_ids: set, k: int) -> float:
    """NDCG@K = DCG / IDCG，归一化后考虑排序位置的重要性"""
    def dcg_at(ids):
        score = 0.0
        for i, doc_id in enumerate(ids[:k]):
            if doc_id in relevant_ids:
                score += 1.0 / math.log2(i + 2)  # i+2 因为位置从1开始
        return score
    idcg = dcg_at(list(relevant_ids)[:k])
    dcg = dcg_at(retrieved_ids)
    return dcg / idcg if idcg > 0 else 0.0

# ========== 查询分类覆盖 ==========

QUERY_TYPES = {
    "factual": "问事实类：什么、是哪个、有哪些",
    "procedural": "问方法类：如何、怎么、步骤",
    "comparative": "对比类：区别、差异、比较",
    "conceptual": "概念类：什么是、解释、定义",
    "troubleshooting": "排障类：报错、解决、修复",
}
```

### 3.4 新增脚本三：test-e2e-rag.py

**目标**：端到端 RAG 流程的完整压测，涵盖检索+生成一条龙。

```python
"""
端到端 RAG 压测脚本

测试流程：
1. 端到端延迟：调用 SSE 接口，记录 TTFT 和总耗时
2. 并发 QPS：阶梯增加并发，找到吞吐量拐点
3. 质量回归：每批压测后抽样 5% 做质量评分
4. 降级保护：模拟 Embedding API 超时，验证优雅降级

SSE 接口压测：
  - 拦截 SSE 流式响应
  - 记录每个 token 的到达时间
  - 计算 TTFT（Time To First Token）
  - 计算 tokens/s 流式速率

降级测试用例：
  | 故障场景 | 预期行为 |
  |---------|---------|
  | Milvus 不可用 | 仅走 ES BM25，降级提示"语义检索暂不可用" |
  | ES 不可用 | 仅走 Milvus 向量检索 |
  | 两路都不可用 | 返回"检索服务暂不可用" |
  | Embedding API 超时 | 重试 3 次，超时后降级为关键词匹配 |
  | LLM API 超时 | 30s 超时，返回已生成部分+"（生成中断）" |

使用方法：
python test-e2e-rag.py
python test-e2e-rag.py --concurrency=10 --duration=120
python test-e2e-rag.py degradation  # 仅跑降级测试
"""

async def measure_sse_latency(session, query: str, kb_id: str):
    """测量 SSE 流式响应的各阶段延迟"""
    url = f"{BASE_URL}/api/v1/rag/v3/chat"
    first_token_time = None
    last_token_time = None
    token_count = 0
    token_times = []

    async with session.post(url, json={...}) as resp:
        async for line in resp.content:
            t = time.time()
            if first_token_time is None:
                first_token_time = t  # TTFT
            last_token_time = t
            token_count += 1
            token_times.append(t)

    total_latency = last_token_time - first_token_time
    tokens_per_second = token_count / total_latency if total_latency > 0 else 0
    return {
        "ttft_ms": (first_token_time - start) * 1000,
        "total_latency_ms": (last_token_time - start) * 1000,
        "token_count": token_count,
        "tokens_per_second": tokens_per_second,
    }
```
